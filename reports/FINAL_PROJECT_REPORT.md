# Final project report: AI-Powered Encrypted Network Traffic Classifier

## Problem and objectives

Encrypted traffic hides payloads while leaving some flow and protocol metadata visible. This project demonstrates collection, conservative service identification, and two separate traffic classification tasks on Windows. It aims to show evidence and uncertainty clearly, rather than claim that a model prediction proves a website or executable identity.

## Architecture and technology

Windows 11 with Npcap supplies packets to NFStream in an isolated Python capture worker. The worker emits bounded flow records to the Streamlit dashboard. nDPI application metadata and observed hostnames feed a rule-based service identifier; unmatched and conflicting evidence remain Unknown or Ambiguous with reasons. A bounded, read-only Windows socket sampler optionally associates a completed flow with a process when protocol, both endpoints, and capture time match. A saved scikit-learn Random Forest separately estimates one of five historical application classes from 61 numeric flow features. Uploaded Scenario B CSV/ARFF data uses a saved XGBoost model with 23 time-based features to estimate one of seven traffic categories. The dashboard also supports offline PCAP/PCAPNG extraction, charts, recent-flow CSV export, a local blocklist, and separately confirmed Windows Firewall and hosts-file enforcement.

## Datasets and model evaluation

Both local archives derive from the [UNB ISCXVPN2016 dataset](https://www.unb.ca/cic/datasets/vpn.html), but support different prediction tasks. The Random Forest dataset contains 115,716 flows from 23 filename-labelled non-VPN PCAPs across AIM Chat, Email, Facebook Audio, Facebook Chat, and Facebook Video. The saved model's 16/7 PCAP-name train/test split scores **56.72% accuracy**, **56.73% balanced accuracy**, and **0.506 macro F1** on 952 test flows. Related recording segments cross that split for 856 test rows, and 444 test rows share an identical processed feature vector with training. It is therefore not an independent five-class session result.

A separate, inferred session-group split used 1,618 held-out flows. A freshly trained baseline scored **36.34% accuracy**, while a deduplicated, source-capped RF candidate scored **34.18%**. The candidate performed worse and remains isolated under ignored `models/experiments/`; the dashboard still loads the original saved RF. This comparison does not establish that the original model generalizes to modern services.

Scenario B has 18,758 labelled ARFF rows in seven categories: BROWSING, CHAT, FT, MAIL, P2P, STREAMING, and VOIP. The saved XGBoost model reproduces **91.20% accuracy**, **88.75% balanced accuracy**, and **0.887 macro F1** on 3,752 rows from its original stratified random-flow 80/20 split (`random_state=42`). The archive has no capture/session IDs, and 170 test rows have a feature vector also present in training. The 91.20% result is a reproducible recorded-split score, not an independent live-traffic guarantee. XGBoost was not retrained.

Per-class support, precision, recall, F1, confusion matrices, feature hashes, and reproducibility steps are in the [model audit](model_evaluation/README.md) and its CSV/JSON artifacts.

## Working features and limits

The dashboard has three views. **Monitor** selects a Npcap interface, starts and stops one background capture worker, updates completed-flow counts and service charts, and provides searchable recent connections with service, hostname, process evidence, status, and traffic usage. Technical endpoints, nDPI details, Unknown reasons, and RF historical-class estimates are expandable. **Analyze file** validates content and model schema before routing one PCAP/PCAPNG/ZIP/CSV/ARFF upload to NFStream, RF, or Scenario B. It shows service evidence when available and exports a report with a privacy acknowledgement. **Settings** contains adapter preference, recorded per-class model metrics and on-demand Scenario B split evaluation, plus advanced blocking configuration. Monitor places a compact Blocking & Protection section directly below Website & application usage, with observed-hostname and remote-IP actions, manual Website / Domain / IP previews, active-rule status, and Undo. Both views share one backend and runtime intent ledger. Enforcement requires a target-specific confirmation, and managed firewall rules or hosts entries can be removed through Unblock actions.

Service coverage depends on observable nDPI and hostname metadata. HTTPS, QUIC/HTTP/3, encrypted DNS, ECH, shared CDNs, DNS-only observations, and missing server names can leave flows Unknown or Ambiguous. A contacted hostname does not identify the Windows executable. Process attribution requires a socket observation during the flow; short-lived, unconnected UDP, permission-limited, and offline flows remain Unknown Process. A matched browser process does not reveal a tab. A model confidence value is not calibrated proof. RF training flow settings differ from short live capture windows. Scenario B lacks a session-held-out evaluation. Neither model establishes production readiness.

## Demonstration and reproducibility

Follow the [Windows setup in README](../README.md#windows-11-setup-and-launch), then run `py -3.13 -m venv .venv`, `.\.venv\Scripts\python.exe -m pip install -r requirements.txt`, and `.\.venv\Scripts\python.exe -m streamlit run dashboard.py` in PowerShell. In **Monitor**, select the active Npcap interface, start monitoring, generate a browser connection, inspect hostname/service/evidence and process only when verified by socket evidence, expand the separate RF estimate, export recent flows only to a private location, stop, and restart. In **Analyze file**, upload a suitable PCAP and a compatible Scenario B CSV/ARFF. In **Settings**, display the separate model reports and optionally recalculate the recorded Scenario B split. In Monitor, preview a blocklist entry without enforcing it. Explain the exact hostname or IP coverage, confirmation, and Undo rollback. A public demo can show the preview and intent without changing real firewall or hosts settings.


Run `.\.venv\Scripts\python.exe -B -m unittest discover -s tests -v` and `.\.venv\Scripts\python.exe -B tools\evaluate_models.py` to reproduce tests and model audit. The optional `TRAFFIC_TEST_PCAP` environment variable enables PCAP integration tests; the README gives commands. Physical Npcap capture, adapter permissions, and firewall/hosts enforcement must be checked separately on the demonstration machine.

Other Wi-Fi background flows were observed, but this run cannot establish a new website detection rate or false-positive rate. Browser disconnect cleanup, prolonged capture, and real enforcement still require machine-specific manual checks.

## Blocking & Protection release update

The three Streamlit views now share a restrained deep-blue (`#1536A6`) and cyan (`#06B6D4`) design. Monitor provides the everyday device-local Blocking & Protection controls, while Settings retains advanced options. The Monitor quick actions fill only an exact observed hostname or a remote IP with one verified local flow endpoint; they never enforce from a Random Forest prediction. IP preview accepts IPv4/IPv6, defaults to outbound, and makes inbound an explicit advanced choice. It checks the device's own addresses, default gateways, and active DNS resolvers before enforcement; critical targets require an extra acknowledgement, while special addresses are refused. The backend verifies exact managed firewall rule properties and refuses duplicate, disabled, or conflicting rules. Domain and website proposals show the exact managed hosts entries; website proposals require recent direct hostname evidence and never include shared CDN IPs or RF predictions. The table distinguishes a saved intent from a verified enabled local rule, records its creation date, and routes undo through a confirmation dialog.

The confirmation and rollback paths are covered by mocks and temporary hosts/blocklist files. No real firewall rule or production hosts entry was changed in automated validation. Live enforcement remains an authorized, elevated manual check on the demonstration computer. An enabled local rule or hosts entry is not proof that every connection to a website will fail, and these controls do not protect other devices on the network.

## Historical usage and activity alerts update: 2026-11-02

Monitor now separates selected-device-adapter OS throughput from completed NFStream flow accounting. It provides period selection, a measured bandwidth chart, optional persisted service/process summaries, usage filters and recent in-memory remote destinations. Exact local endpoint information provides direction independently of process attribution; loopback, both-local endpoints and ambiguous counters retain unknown direction. Counter resets and stale/missing samples produce no current rate.

Local SQLite history defaults to seven-day retention with WAL, parameterized queries, row caps and explicit deletion. Service/process names are opt-in; endpoint addresses, hostnames, executable paths and payloads are not persisted. A bounded ingestion queue separates database work from capture, stable capture-event IDs prevent rerun duplicates, and a database lease coordinates overlapping app instances. Lock/corruption/overflow failures leave visible history gaps while capture continues. Separate databases cannot coordinate their traffic totals. Stored data is local and unencrypted.

The five configurable alert types cover new identified services, reliably attributed processes, Mbps/data thresholds, repeated connections to a chosen destination and managed-rule state changes. Informational events and warnings have cooldowns, deduplication, local history, read/dismiss/clear controls and bounded dashboard toasts. Blocking inspection is read-only; unknown traffic is never treated as malicious and no alert automatically enforces a rule.

A final physical check used the selected active Windows device adapter in 16-second and 8-second sessions. The first session completed **four flows / 13,071 flow bytes**, all four with reliable direction and two with exact process attribution. The shorter restart session completed no flows; it verifies clean restart/stop only, not a detection rate. Both sessions stopped without capture errors. Across the two sessions, **11 OS counter intervals** measured **373,634 received / 292,655 sent bytes**, with observed peak interval averages of **0.260 Mbps download / 0.573 Mbps upload**. Counter totals include other traffic on that adapter and differ from completed flows; they must not be added or interpreted as link capacity. Only aggregate results are documented; no private endpoints, adapter identifiers or capture files are published. No production firewall or hosts entry was changed.

The automated review covers synthetic rates/resets/direction, SQLite restart/retention/clearing/locks/corruption/concurrency, alert thresholds/cooldowns/read state, duplicate prevention, capture lifecycle and Streamlit reruns. Existing PCAP integration tests run on a generated synthetic PCAPNG. Final validation passed **150 tests with zero skips**, including both NFStream integrations on the synthetic PCAPNG, **57 syntax checks**, **28 backend imports**, exact dependency/compatibility checks and HTTP 200 responses for Streamlit health/root. Concurrent alert cooldown updates are serialized in SQLite so multiple readers cannot create duplicate records. Flow-usage thresholds aggregate busy seconds without dropping recorded byte counts; their bounded one-second buckets can include one extra boundary second. The temporary server was stopped.

## Privacy and future work

Flow rows can contain personal IP addresses, hostnames, user agents, process paths, and timing metadata. Keep live exports, capture files, logs, and the runtime blocklist outside Git and sanitize screenshots. The cleaned GitHub `main` and `development` histories were published on 2026-11-02; this checkout uses that cleaned lineage. Old commit and file references remained accessible after publication and require GitHub Support review for server-side removal. Rewritten branch history does not erase prior exposure or copies held elsewhere. Never merge or publish the original contaminated history into this cleaned repository.

Future work needs independently labelled capture sessions for every RF class, modern service classes, matching live/train flow windows, a locked external test set for both models, and broader physical validation of process attribution across adapters, short-lived connections, IPv6, and permission profiles.
